Solar Charging for Golf Carts

Solar Charge Controller

Project Description

  • A solar charge controller for golf carts that charges the vehicle battery from roof-mounted solar panels, extending driving range and reducing dependence on grid charging.
  • It supports multiple battery types with CC/CV charging and communicates with the vehicle control unit (VCU) over CAN.
  • Role Firmware Lead
  • Period Sep 2026 - Present
  • Team size 2

Key Features

  • Solar charging with CC/CV control through a dedicated charge controller IC
  • Battery voltage and temperature monitoring with fault protection
  • CAN interface that lets the VCU set the charge current, voltage limit and charge permission
  • Firmware update over CAN with recovery from interrupted updates
  • MPPT control algorithm to maximize power harvested from the solar panels

My Responsibilities

  • Lead firmware development from requirements analysis to release
  • Analyzed product requirements and the charge controller IC specification
  • Designed a layered firmware architecture
  • Developed low-level drivers (GPIO, ADC, CAN, I2C), including an interrupt-driven, queue-based asynchronous I2C driver
  • Implemented the charge controller service and transport layers, battery monitoring, calibration data and error handling
  • Added CAN communication with the VCU and charge voltage selection per battery type
  • Implementing firmware reprogramming over CAN using boot swap and the Renesas Flash Self-Programming Library
  • Led integration testing and phase reviews, and coordinated development tasks with the team

Technical Challenges & Solutions

  • Non-blocking communication with the charge controller: blocking I2C transfers kept the CPU waiting and could hang the system when the bus failed. I designed an interrupt-driven, queue-based asynchronous I2C driver with callbacks, which increases processing speed and ensures the bus always recovers after an I2C failure.
  • Safe firmware update on a 48 KB MCU: limited flash and the risk of a power loss during an update. I defined a manual memory layout with boot clusters and boot swap, so the write program runs from RAM and the previous firmware stays valid until the new image is verified.
